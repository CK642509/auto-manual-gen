# STYLE

手冊正文（`docs/{order}-{id}.md`）的寫法。它同時是給人審稿用的檢查清單，也是給 agent 的上下文——
改寫法就改這份檔案與 `docs/` 裡的範例，不要只改 prompt。

## 資料來源

- **只根據本章的 manifest、截圖，以及 `agent/`、`TESTID.md`、i18n 文案撰寫。**
  資料裡找不到證據的功能、步驟、限制，一律不寫；覺得「應該要有」的內容，回報給人，不要自己補。
- manifest 的步驟是操作順序的真相來源。正文的步驟順序要跟 manifest 一致，不增、不減、不換順序。
- 如果發現 manifest、截圖、i18n 三者對不上（例如 legend 跟畫面上的字不同），**不要自己挑一個寫**，
  照 manifest 寫完後把差異回報給人。

## 讀者

- 讀者是 DemoStreamApp 的操作員，不是工程師。
- testid、component 名稱、Vue / Playwright / runner 的行為**只能用來理解上下文，不能出現在正文**。
  `waitFor`、`fill` 這些動詞要翻成讀者看得到的結果，例如 `waitFor: toast` →「畫面出現成功通知」。
- 不描述會變動的數值（推論 FPS、偵測到的物件數、時間戳）。截圖裡看得到，但每次都不一樣。

## 用詞

- 繁體中文，台灣用語。
- **有標號的元件，用 `{{legend.<key>}}` 引用，外面加「」。** 例如 `點擊「{{legend.confirm}}」`。
  合併正文時會換成本章 legend 的文字，所以正文裡不要寫標號數字，也不要把 legend 文字抄進來。
- **沒有標號的元件，名稱直接取自 `apps/demo-stream-app/src/renderer/locales/zh-Hant.json`，外面加「」。**
  畫面上寫「建立」就寫「建立」，不要潤飾成「確認新增」「按下儲存」。
- 動作用「點擊」「雙擊」「輸入」「選擇」「開啟」，不用「按下」「點選」「打開」。
- 示範用的輸入值（例如「大門西側」）照 manifest 寫，加「」。

## 句型

- 操作步驟用祈使句：寫「點擊「{{legend.confirm}}」」，不寫「使用者可以點擊……」。
- 一個動作一行，用編號清單。一行裡不要用「然後」「接著」串兩個動作。
- 用途簡介一到兩句，說明「這一章做完可以得到什麼」，不寫背景故事。

## 截圖

- 用 `{{screenshot:<name>}}` 放圖，獨立一行，`<name>` 就是 manifest 裡 `screenshot` 步驟的 `name`。
- 放在它所對應的操作步驟**之後**：讀者先讀到要做什麼，再看到做完長什麼樣子。
- 截圖要打斷編號清單時，後面的清單接續編號（`3.` 而不是重新從 `1.` 開始）。
- manifest 裡每一張截圖都要出現一次，不能漏、不能重複。

## 骨架

每一章都用這個結構，不要自己增加小節：

```markdown
# <manifest 的 title>

<用途簡介，一到兩句>

## 操作步驟

1. <步驟>
2. <步驟>

{{screenshot:<id>-01}}

3. <步驟>

## 完成後

<讀者應該看到什麼，用來確認自己做對了>

> 注意：<真正會影響操作的限制或前置條件；沒有就整段省略>
```

- 「完成後」只寫畫面上看得到的結果。
- 「注意」只寫會讓讀者操作失敗或誤解的事，最多三點，沒有就省略，不要為了填滿而寫。

## 範例

已經人工審核通過的章節就是範例，寫新的一章之前先讀：

- `docs/20-live-monitor.md`
- `docs/40-settings.md`

模仿它們的結構、句子長度與語氣，但不要複製其中的產品內容。
